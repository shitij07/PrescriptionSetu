## Known Issues / Blockers

- **Toolchain constraints (both real; deliberately **not** decision-log entries — MASTERPLAN §19 already authorises Node/TS/Jest, D-001 fixes TypeScript and D-026 fixes npm, so these are dependency-compatibility facts, not decisions).** (a) **`npm test` runs on the Windows host only, never in an agent's Linux sandbox** — `jest-resolve@30.4.x` resolves through `unrs-resolver`, a native NAPI binding, and only `@unrs/resolver-binding-win32-x64-msvc` is installed (the linux-x64-gnu entry is optional in the lock and absent). The symptom lies: `Module ts-jest in the transform option was not found` even though `node_modules/ts-jest` is present (29.4.12, confirmed 2026-08-27), reproduced with `babel-jest` and absolute paths, so it is **not** a `jest.config.js` defect. Do **not** delete the lockfile as the unrs error suggests — regenerating on Windows reinstalls the same Windows-only binding. `tsc` is pure JS and does run in-sandbox, so typecheck is agent-verifiable and Jest is not. (b) **TypeScript is pinned `~5.9.3`** because ts-jest 29 needs the classic `require('typescript')` compiler API that **TypeScript 7 removed** (under 7.0.2 the `"."` export is `lib/version.cjs`, so `transpileModule`/`createProgram`/`createLanguageService` are `undefined`); TS cannot move to 7.x while ts-jest 29 is the transform layer. Non-blocking: Jest metadata says 30.4.2, its CLI reports 30.4.1.
- **Open safety questions (unresolved):** **OQ-02** RESOLVED by D-030; OQ-03 OCR confidence threshold (start 0.70, tune once corpus exists); OQ-05 caregiver↔patient auth (SI-10 stop *authz*); OQ-06 `meal_times` shape; OQ-07 image encryption/signed-URL → `ARCHITECTURE.md`; OQ-08 dead-end `needs_attention` escalation; OQ-10 `stat` administration owner; OQ-11 is letter case semantically meaningful (`HS` vs `hs`) — case folding assumes not; OQ-12 Marathi native review; **OQ-13** persist `dictionary_version` (in `parse_result` only for now).
- **Discovered gaps, `API_CONTRACTS.md` §14 (one resolved):** #1 no dictionary rule authorises **drug-name extraction**, yet MASTERPLAN §18.3 and `medications.drug_name` expect it (D-025) — `drug_name` has no producer at end of Phase 1; #2 envelope-level `unparsed_fragments` have **no storage location** (must not be discarded to make persistence succeed); #3 **no rule sets `schedule_derivable: true`**, so the parser alone never authorises a schedule; #4 "medication line" undefined though dictionary §7.1 / D-012 depend on it; #5 dictionary §2 lists the two SI-08 ceiling fields (patch-level clarification owed); #6 dictionary §4 does not state case folding is locale-invariant — the **code** now folds ASCII-only via `foldAsciiCase` (never `toLowerCase`/`toLocaleLowerCase`, which can fold non-ASCII *into* the ASCII range and manufacture a match), so the doc clarification is still owed but the implementation no longer depends on it; **#7 RESOLVED 2026-08-27 by D-029, marked in §14.10.**
- **Parser debts, disclosed rather than hidden.** (a) `1 tab BD` reports `dose_amount` as `absent_from_prescription` and raises `verifier_action_required` **even though the text says `1 tab`** — a false statement about the source text, caused by `AMT-TAB-001` being unimplemented. It errs toward routing *more* to the human and self-corrects when that rule lands; owner-accepted for this slice. (b) **Unparsed-fragment reporting is unimplemented** (dictionary §10, SI-06, §11 case 22): `Metformin` in `Metformin 500 mg BD` is neither attributed nor reported. Nothing is destroyed (`parse` is pure, the caller still holds the text) but nothing is surfaced either. (c) Dictionary §9's other three rows and §8 conflict resolution are unreachable with two non-overlapping rules and are left as comments, not dead code. (d) Multi-sentence input such as `BD.OD` is untested; D-029 makes edge validation load-bearing.
- **`source_span` retention dependency:** offsets resolve against `prescriptions.raw_ocr_text`, but §26 retention names only raw *images* for deletion → deletion would dangle every stored span (`matched_literal` survives, offsets do not). DPDP erasure soft-vs-hard undesigned. Settle with the retention/erasure design.
- **Bhashini onboarding not started** — gates Phase 3; submit early. **WhatsApp business-initiated rules unverified** — may need pre-approved per-language templates (bounded variables), changing the `reminders` schema; confirm vs Twilio/Meta docs *before* schema work (`BUILD_ORDER.md` §3).
- **Operational Limitation (PostgreSQL → Redis Atomicity):** Sub-Slice 2B implementation relies on generating and persisting reminders in PostgreSQL, and then enqueuing them into Redis (BullMQ). This lacks true atomicity (an outbox pattern was explicitly rejected to avoid overbuilding per Issue 8). If the process crashes after PostgreSQL commit but before Redis enqueue, the reminder will be persisted but not enqueued. This is a known operational limitation and accepted risk for this phase.
